# 시니어클럽 제품 요구사항

> 문서 상태: 구현 기준선 · 2026-07-30  
> 제품 원칙: **목적 → 사람 → 활동 → 관계**

## 1. 제품 한 문장

시니어클럽은 같은 관심사와 활동 목적을 가진 시니어와 중장년이 가까운 모임을 찾고 안전하게 참여한
뒤, 채팅·후기·다음 활동으로 관계를 이어 가도록 돕는 커뮤니티다.

성공 기준은 정보 조회 수가 아니라 다음 행동이다.

1. 관심사와 활동 지역을 정한다.
2. 공개 커뮤니티와 모임을 찾는다.
3. 본인 인증 계정으로 신청하고 활동에 참여한다.
4. 대화와 후기로 관계를 이어 간다.

## 2. 사용자와 핵심 과업

| 사용자 | 가장 중요한 과업 | 제품이 보장할 것 |
| --- | --- | --- |
| 일반 회원 | 맞는 모임을 찾고 신청 | 쉬운 탐색, 정원·난이도·준비물, 본인 신청 상태 |
| 리더 | 담당 모임과 참가자를 운영 | 초안·공개·취소, 승인·거절, 출석, 모임 채팅 |
| 관리자 | 안전 신고를 처리 | 신고 목록·상태 처리와 변경 감사 기록 |

전역 역할은 `MEMBER`, `LEADER`, `ADMIN`이다. 커뮤니티 역할은 별도의 `MEMBER`, `MODERATOR`,
`LEADER`이며, 전역 `LEADER`만으로 다른 커뮤니티를 운영할 수 없다.

## 3. 현재 구현 범위

| 영역 | 구현된 범위 | 출시 전 남은 조건 |
| --- | --- | --- |
| 계정 | 휴대폰 SMS OTP, access/refresh 회전, 로그아웃 | production Twilio 실전 검증 |
| 온보딩 | 이름, 출생연도, 지역, 관심사와 약관 동의 | 실제 운영 약관·개인정보 문구 확정 |
| 탐색 | 공개 커뮤니티·모임 목록/상세, 검색·필터·cursor | production catalog와 운영 데이터 |
| 신청 | 로그인·온보딩 후 신청/취소, 자동·수동 승인, 정원 transaction | 실제 PostgreSQL 동시성 E2E |
| 리더 | 모임 초안/수정/공개/취소, 신청 결정, 출석 | 실사용 역할별 E2E |
| 게시판 | 텍스트 게시글·댓글·답글 CRUD | 미디어 업로드는 현재 범위 아님 |
| 후기 | 참석 자격, 1~5점, 텍스트 후기 CRUD | 실제 출석→후기 운영 E2E |
| 채팅 | 승인 참가자·운영진 방, REST 이력/증분, Socket.IO, 읽음 | 다중 API 인스턴스 전에는 단일 fan-out 경계 유지 |
| 알림 | 인앱 목록/읽음, 수신 설정, Android FCM token | Firebase client/Admin 자격 증명과 실기기 수신 |
| 안전 | 콘텐츠·사용자 신고, 사용자 차단/해제, 관리자 신고 처리 | 운영 담당자·SLA·제재 절차 확정 |
| 계정 삭제 | 앱·웹 요청, 7일 유예, 즉시 session·push 해제 | production DB·백업 삭제 E2E |
| 광고 | Android 홈·모임 목록 배너, 플러스 구매 시 숨김 | 전면 광고 없음 |
| 앱 내 결제 | 광고 제거 일회 구매 `seniorclub.remove_ads` | 모임 참가비 Play 수납, 웹 결제 |

공개 화면은 API를 사용할 수 없을 때 fixture 일정이나 회원 상태를 대신 표시하지 않는다. 기기·브라우저
저장 값은 session 복원과 표시 속도를 위한 cache일 뿐이며 권한·정원·신청·출석의 원본은 API와
PostgreSQL이다.

## 4. 현재 출시 범위가 아닌 기능

- 카카오·네이버·Google OAuth와 계정 연결
- 사용자 사진·파일 업로드, S3, 카메라·미디어 권한
- 앱 내 구독(월 자동 결제)과 모임 참가비의 Play Billing 수납
- 친구 관계와 친구 활동 추천
- 지도 기반 거리 계산
- 관리자 회원 정지·권한 변경, 직접 콘텐츠 숨김, 통계 dashboard
- 뉴스레터 작성·예약 발송 UI
- Redis Socket.IO adapter를 사용하는 다중 인스턴스 fan-out

이 기능은 스토어 설명에 약속하지 않는다. 추가하는 릴리스에서 별도 API, 권한, 개인정보 처리방침과
Data Safety 검토를 함께 진행한다.

## 5. 핵심 사용자 여정

### 5.1 탐색과 신청

1. 비로그인 사용자는 공개 커뮤니티와 모임을 살펴본다.
2. 신청을 누르면 웹·앱 모두 휴대폰 SMS OTP 로그인으로 이동한다.
3. 첫 사용자는 이름·출생연도·지역·관심사를 저장한다.
4. 원래 선택한 모임으로 돌아와 신청한다.
5. 자동 승인 모임은 `APPROVED`, 수동 승인 모임은 `PENDING`이 된다.
6. 결과는 내 신청과 인앱 알림에 저장되고, 설정에 따라 선택적 이메일·FCM outbox가 생성된다.

동일 신청의 재시도는 `Idempotency-Key`로 한 결과만 만들며, 정원·마감·중복 상태는 서버 transaction에서
판단한다.

### 5.2 리더 운영

1. 리더는 자신이 운영하는 활성 커뮤니티를 선택한다.
2. 모임을 초안으로 저장하거나 즉시 공개한다.
3. 신청자를 승인·거절하고 승인 인원이 정원을 넘지 않도록 서버가 직렬화한다.
4. 현장에서 `ATTENDED` 또는 `NO_SHOW`로 출석을 기록한다.
5. 모임 취소 시 남은 신청 상태, 일반 참가자의 채팅 권한, 인앱·이메일·푸시 알림을 한 transaction에서
   갱신한다.

현재 API는 `DRAFT → PUBLISHED` 공개와 `DRAFT|PUBLISHED|CLOSED → CANCELED` 취소를 제공한다.
`CLOSED`, `COMPLETED`로 직접 전환하는 운영 API는 아직 없다.

### 5.3 활동 후 관계

1. 승인·출석 회원에게 후기 작성 자격이 열린다.
2. 회원은 1~5점과 10~800자의 텍스트 후기를 모임당 하나 작성한다.
3. 승인 참가자와 현재 운영진은 모임 채팅을 계속 이용한다.
4. 다음 모임은 공개 catalog에서 확인한다.

현재 홈은 실제 공개 모임 중 정해진 대표 관심사 카드를 보여 준다. 관심사·지역·참여 이력 점수 기반
개인화 추천은 목표 기능이며 아직 production 추천 API로 제공하지 않는다.

## 6. 권한 정책

화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않는다. API는 활성 session, 전역 역할, 소유권,
커뮤니티 운영 관계, 리소스 상태를 매 요청 다시 검사한다.

| 작업 | 회원 | 리더 | 관리자 |
| --- | :---: | :---: | :---: |
| 공개 커뮤니티·모임·게시글·후기 조회 | O | O | O |
| 본인 프로필·관심사·알림 설정 | O | O | O |
| 온보딩 후 게시글·댓글 작성 | O | O | O |
| 본인 게시글·댓글·후기 수정/삭제 | O | O | O |
| 모임 신청·취소 | O | O | O |
| 모임 생성·수정·공개·취소 | X | 담당 커뮤니티 | 권한 검사를 거친 관리 범위 |
| 신청 승인·거절·출석 | X | 해당 모임 운영자 | 권한 검사를 거친 관리 범위 |
| 모임 채팅 | 승인 참가자 | 해당 모임 운영자 | 자동 우회 권한 없음 |
| 후기 작성 | 출석 회원 | 출석한 경우 | 출석한 경우 |
| 신고·차단 | O | O | O |
| 신고 상태 처리 | X | X | O |

관리자에게 비공개 채팅을 임의 열람하는 endpoint는 없다. 현재 관리자 기능은 신고 조회·상태 처리와
감사 로그에 한정된다.

## 7. 상태와 데이터 규칙

### 모임과 신청

```text
DRAFT ──공개──> PUBLISHED ───────────────> CANCELED
  └──────────────────────────────────────> CANCELED

PENDING ──승인──> APPROVED ──출석──> ATTENDED | NO_SHOW
   ├──거절──> REJECTED
   └──회원 취소──> CANCELED
```

- `(eventId, userId)` 신청과 후기는 각각 유일하다.
- 승인 수가 정원에 도달하면 추가 승인을 원자적으로 막는다.
- 거절 사유는 2~500자이며 민감정보를 적지 않는다.
- 후기 작성에는 승인과 `ATTENDED` 기록이 모두 필요하다.
- 사용자 삭제 동작은 게시글·댓글·후기를 `HIDDEN`으로 전환하는 soft delete다.

### 신고와 차단

- 신고 대상: `USER`, `POST`, `COMMENT`, `REVIEW`, `CHAT_MESSAGE`
- 신고 상태: `OPEN → IN_REVIEW → RESOLVED | DISMISSED`
- 같은 사용자의 열린 중복 신고는 직렬화해 `409 REPORT_ALREADY_OPEN`으로 막는다.
- 본인·본인 콘텐츠 신고와 본인 차단은 허용하지 않는다.
- 차단은 계정당 최대 500명이다.
- 모바일은 콘텐츠 신고, 사용자 신고, 사용자 차단을 분리해 제공한다.
- 채팅은 양방향 차단 관계를 history, 방 preview, socket fan-out에 적용한다.

## 8. 알림과 연락

- 신청 승인·거절, 일정·모임 취소, 후기 요청은 인앱 알림과 outbox를 사용한다.
- 푸시는 사용자가 허용한 실제 Android 기기의 FCM token만 등록한다.
- 푸시·이메일 수신 설정을 서버에 저장한다.
- 발송 실패는 사용자 transaction을 되돌리지 않으며 worker가 제한적으로 재시도한다.
- production 자격 증명 없이 실제 SMS·이메일·푸시가 동작한다고 표시하지 않는다.

## 9. 접근성·성능·보안 요구

### 접근성

- 기본 본문과 주요 상태 문구를 크게 제공하고, 조작 영역은 최소 44×44px를 목표로 한다.
- 색만으로 상태를 구분하지 않고 텍스트·아이콘을 함께 사용한다.
- 웹 핵심 흐름은 키보드와 스크린리더 상태 영역을 지원한다.
- Android는 명확한 뒤로 가기, 오류·빈 상태, 큰 글자 설정을 제공한다.

### 성능과 비용

- 공개 목록은 짧은 공유 cache와 cursor pagination을 사용한다.
- 개인·관리 응답은 `private, no-store`다.
- 채팅은 `after` 증분 조회와 주기적 전체 정합성 검사로 전체 재다운로드를 줄인다.
- sitemap은 최대 페이지 수를 제한하고 한 시간 재사용한다.

### 보안과 개인정보

- 웹 token은 `HttpOnly`, `Secure`, `SameSite=Lax` cookie에 둔다.
- Android refresh token은 SecureStore, access token은 메모리에 둔다.
- 모든 변경 요청은 인증·권한·strict 입력 검증을 적용한다.
- OTP, JWT, DB URL, Twilio/Resend/Firebase secret을 저장소·URL·로그에 남기지 않는다.
- 정밀 위치, 연락처, 통화·문자, 건강·음성, 신용카드 번호, 사용자 사진·파일을 현재 수집하지 않는다.

## 10. 측정 지표

북극성 지표는 최근 90일 안에 서로 다른 두 번 이상의 오프라인 모임에 출석한 월간 활성 회원 수다.

핵심 퍼널:

1. OTP 인증 완료율
2. 온보딩 완료율
3. 모임 목록 → 상세 전환율
4. 상세 → 신청 전환율
5. 신청 → 승인율
6. 승인 → 출석률
7. 출석 → 후기 작성률
8. 첫 출석 후 30일 내 재출석률

신고 처리 시간, 모임 취소율, 노쇼율, 발송 실패율을 안전·운영 지표로 함께 본다.
